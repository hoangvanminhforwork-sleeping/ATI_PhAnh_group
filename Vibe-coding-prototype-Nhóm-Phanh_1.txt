Smart Document Processing Playground

Build a polished single-page web application called Smart Document Processing Playground.

The application is a frontend prototype demonstrating an AI-powered document processing pipeline:

Input: invoices / receipts / business documents as images or PDFs
Processing: multimodal LLM API or mock processor
Output: structured JSON / JSONL

This is a prototype. It should visually and behaviorally resemble a batch-processing system, but it does not need a real batch API, distributed queue, authentication system, database, or server-side batch infrastructure.

Each document may be processed using a normal realtime multimodal API request.

The architecture must keep the processing engine isolated so a real backend queue/batch system can be introduced later without redesigning the UI.

1. Core Product Concept

The most important concept of the application is:

Each JSONL item on the left represents an independent processing job that can be played, paused, stopped, monitored, and inspected.

The application should feel like a combination of:

AI developer tool

file manager

media player

batch-processing dashboard

JSON/JSONL inspector

Avoid making it look like a generic CRUD/admin dashboard.

The application should feel polished, technical, modern, and believable.

14. Processing Engine

The application should visually behave like a batch-processing system.

However, it does NOT need a real batch API.

When a job starts:

Iterate through selected documents sequentially.

Send a realtime multimodal API request for each document.

Include: 

system prompt

selected model

document/image

expected JSON schema

Receive the model response.

Parse response as JSON.

Validate JSON.

Store the result.

Append result to the job's JSONL output.

Increment progress.

Continue with the next document.

Conceptually:

document_001.jpg ↓ realtime multimodal API request ↓ LLM ↓ structured JSON ↓ validate JSON ↓ append to JSONL ↓ progress = 1 / N ↓ document_002.jpg ↓ ... 

15. Processing Adapter Architecture

Do not tightly couple the UI to the API implementation.

Create an isolated processing adapter.

Example:

const documentProcessor = { async processDocument(document, config) { // implementation } } 

The job-processing engine should only communicate with this interface.

This allows the mock processor to later be replaced by:

Mock Processor ↓ OpenRouter Processor ↓ Gemini Processor ↓ OpenAI-compatible Processor ↓ Future backend queue 

without changing the UI.

16. Mock Processor

The default prototype processor must be a mock processor.

This allows the application to work immediately without an API key.

The mock processor should:

Receive the document.

Receive the system prompt.

Receive the selected model.

Receive the expected JSON schema.

Simulate network/API latency.

Return structured JSON.

Occasionally return a deterministic failure.

Simulated processing delay:

500–1500ms per document 

The delay should make the processing feel real without making the demo annoying.

17. Deterministic Mock Processing

Do not make mock failures completely random on every render.

The demo should be reproducible.

For example:

invoice_001.jpg → success invoice_002.jpg → success invoice_003.jpg → success invoice_004.jpg → failure invoice_005.jpg → success 

A failed document should return an error such as:

Unable to extract a valid JSON response from the model. 

The job should continue processing subsequent documents.

31. Job State Machine

Implement clear job transitions.

Recommended behavior:

Ready ↓ Play Processing ↓ Pause Paused ↓ Play Processing ↓ Stop Stopped ↓ Play Processing ↓ all documents complete Completed 

A job can also become:

Failed 

if a job-level error occurs.

Individual document failures should not automatically fail the whole job.

32. Pause Semantics

Pause must not interrupt an active API request.

If the current document is being processed:

Pause clicked ↓ finish current request ↓ store result ↓ update progress ↓ do not start next document ↓ status = Paused 

This is important.

Do not abruptly terminate an in-flight request unless cancellation is explicitly supported.

33. Stop Semantics

Stop should prevent future documents from starting.

Already completed documents must remain.

Example:

Before: 8 / 12 

User clicks Stop.

Result:

Stopped 8 / 12 

The eight completed results remain available.

Clicking Play again resumes from document 9.

34. Multiple Jobs

Starting one job must not reset or modify another.

Users should be able to switch between jobs while a job is processing.

Processing should continue independently.
